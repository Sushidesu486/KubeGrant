# 内部权限控制与 kubeconfig 分发开发计划

更新：2026-10-16。用户已同意开始开发；普通凭据采用 24 小时策略，固定运维成员采用长期授权与 1 年证书。提交前仍须确认。

## 交付目标

KubeGrant 是基于 Kubernetes 的内部权限控制平台，向内部成员分发受管理的个人 kubeconfig。平台管理成员、集群、角色与范围、授权、凭据及其执行状态；凭据签发是权限管理闭环的一部分。

管理员分配权限与授权期限，控制器在集群建立对应绑定；成员登录后下载个人 kubeconfig，直接使用 kubectl。平台能追踪凭据归属、签发和到期记录，执行权限撤回与回收，并显示实际结果。保留现有 SSH、BMC 和离线应急入口。

### 授权与凭据的有效期

| 对象 | 普通成员 | 固定运维成员 |
| --- | --- | --- |
| 授权 | 管理员指定到期时间 | 管理员可指定长期有效，不设自动到期时间 |
| 客户端证书 | 默认 24 小时 | 管理员显式选择运维策略，最长 1 年（365 天） |
| 权限来源 | 分配的角色及范围 | 同样由角色及范围决定，长证书不自动赋予 cluster-admin |
| 收权 | 授权到期或手动撤回后清理绑定 | 手动撤回后清理绑定，证书未到期也不能保留该绑定的权限 |

长期授权不等于永不到期的证书。X.509 证书有明确的 `NotAfter`，平台按 1 年策略签发，到期前提醒换领；在不安装登录插件的约束下，旧 kubeconfig 不会自动更新证书，成员需下载替换。短期授权仍限制证书不能越过其授权期限。

长期策略只能由管理员对授权显式分配，不根据下载参数、成员自选或 FreeIPA `admins` 组自动启用。`admins` 继续只表示平台管理资格。证书有效期策略与角色权限分别管理，不新增固定权限档位。

这次按三个阶段交付。第一阶段先建立可测试的凭据核心和设计边界；第二阶段实现持久化任务与控制器；第三阶段接通下载界面并完成集成验收。不能将某一阶段完成当作生产签发已可用。

## 已确定的实现方向

- 首版接入现有单集群；角色由服务端配置映射，不能由下载请求指定 roleRef、证书主体、组或 API 地址。
- 使用 `certificates.k8s.io/v1`、`kubernetes.io/kube-apiserver-client` 签名流程。集群控制面持有 CA 私钥；KubeGrant 不读取或挂载该私钥。
- 每条授权生成独立的 Kubernetes User 主体，不包含任何证书 Organization、UID 或 SAN；平台管理员身份不自动转换为集群管理员。
- 一条授权的多次下载使用相同主体、不同私钥；删除该授权的绑定回收所有这些配置的受管权限。重新授权使用新 ID 和新主体，旧凭据不能因重新授权恢复权限。首版不提供单份下载的独立撤销。
- 证书期限由管理员分配的凭据策略决定：`standard` 为 24 小时，`operations` 为 365 天；有限期授权还会进一步限制到期时间，长期授权则只受证书策略限制。有效期从申请开始计算，签发重试不能把它顺延；实际证书可以更短。授权剩余不足 10 分钟时不再签发，因为 Kubernetes CSR 的 `expirationSeconds` 最小为 600。
- 每次下载在服务端内存生成 ECDSA P-256 私钥。队列和数据库只保存 CSR、公开证书及元数据；不保存私钥，也不提供旧私钥找回。失败后重新下载生成新密钥。
- kubeconfig 使用 JSON 编码（kubectl 支持），嵌入公开 CA、客户端证书和私钥，不包含 exec 插件、外部文件路径或跳过 TLS 验证的选项。

依据：[CSR 与有效期](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/)、[客户端证书身份映射](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/authentication/)。集群只读核验为 Kubernetes v1.35.0，控制面配置了集群签名证书与密钥；本次未读取私钥，未创建或批准真实 CSR。

Kubernetes 内置 signer 的默认签名期限上限为 8760 小时（365 天）；实际签名还受 signer 配置和 CA 有效期约束。接入时核对各控制面的有效配置和公开 CA 到期时间，并以实际签发结果显示期限；不为长期凭据直接修改全局签名期限。[控制器参数](https://v1-35.docs.kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/)

## 阶段 1：凭据核心

交付代码：`internal/credential`。

1. 固定授权与凭据的关联、主体生成规则，以及普通 24 小时、运维 365 天两种凭据策略；验证时采用服务端授予的策略，不能信任任务自行声明的策略。
2. 实现内存私钥、CSR 生成、CSR 严格校验及公钥指纹。
3. 校验签发结果的 CA 链、身份、公钥、客户端用途、有效期；拒绝包含额外身份或超期的证书。
4. 生成自包含 kubeconfig；只对申请时的成员身份和仍有效的同一条授权交付。
5. 使用本地测试 CA 验证成功路径以及越权、撤回、到期、错误签名、密钥不匹配和额外组等拒绝路径。

这一阶段不修改生产配置，不开放下载按钮，不做数据库迁移。

## 阶段 2：持久化任务与独立控制器

### 数据和执行状态

- 升级 SQLite schema；保留用户、会话、授权与审计。迁移前备份，拒绝未知版本；加入 v1 数据库迁移和备份恢复测试。
- 授权增加凭据策略字段；到期时间可空，NULL 表示明确选择的长期授权，不使用虚构的远未来日期。迁移将旧记录保留原到期时间并赋予 standard 策略，不能自动升级成长期授权。
- 领域模型、存储、API 和前端同时适配长期授权；普通有限期授权继续遵循现有授权上限，长期授权由管理员专门选择，不能通过省略到期字段意外创建。
- 新增 CredentialRequest：ID、GrantID、MemberID、ClusterID、凭据策略、主体、CSR、公钥指纹、申请时间、最晚到期时间、CSR 对象名/UID、状态、公开证书和失败代码。没有 private_key 字段。
- 新增 GrantExecution：绑定对象名/UID、最后观察时间、已应用状态、失败代码。授权的意图和集群执行结果分别保存。
- 任务状态为 pending → issued / failed / abandoned；过期或撤回后不能从终态重新签发。写入状态和对应审计采用同一事务与条件更新。
- 控制器遍历全部授权和待处理任务，使用分页；不能复用界面列表的 500 条上限，否则旧授权可能漏收权。

### 控制器职责

- 独立 `kubegrant controller` 进程，不开放 HTTP 接口。首版可作为同 Pod sidecar 共享 SQLite/PVC；只向它显式挂载短期、自动轮换的 ServiceAccount token，Web 容器不挂载。
- 同 Pod 和共享数据库是运维隔离，不是抵御 Web 被攻破的强安全边界；Web 本身能写授权意图，需按权限代理系统保护。
- 仅绑定配置允许的既有 ClusterRole；不复制或修改既有共享绑定、不自动导入历史管理员 kubeconfig、不新建权限档位。
- 每条授权建立一个确定名称的 ClusterRoleBinding，subject 为其独立 User。对账时校验所有权标签、UID、roleRef 和完整 subjects；遇到同名非受管资源报错，不接管。
- 每次审批前重新读取有效授权与数据库任务，校验 CSR、公钥指纹、主体、签名用途、signer 和剩余有效期；只审批自己创建且 UID 一致的 CSR。不能按标签批量批准，也不接受浏览器上传任意 CSR。
- 从授权中重新解析允许的凭据策略，不从 CSR 或任务自报字段选择长有效期；管理员修改策略时，重新校验待签发任务。缩短策略只约束后续签发；如要使已有长证书失去受管权限，撤回原授权并创建新主体，不宣称能修改已签发证书的到期时间。
- 创建 CSR 时重新计算剩余秒数并预留签名延迟；若不足 Kubernetes 最小 TTL 则拒绝。最终仍严格校验证书绝对到期时间，不能用延迟余量放宽授权期限。
- CSR 已批准但签名暂未完成时记录状态并重试；不在控制器中阻塞整个回收循环。重启沿用任务，不重复产生身份或绑定。
- 过期和撤回优先处理，删除受管绑定时使用 UID 前置条件；删除确认后才显示已回收。API 或存储故障保留失败状态并重试。
- 新建/签发后再检查授权，覆盖撤回与签发并发；不能把已撤回的授权标记为已生效或交付下载。
- 启动与周期性全量对账，处理未完成任务及受管孤儿资源。恢复旧备份先停签发，人工核对撤回记录与集群状态，不能直接重放旧授权。

### 权限与部署准备

- 功能显式启用，默认关闭。controller 参数与公开集群 endpoint/CA 分别校验；启动失败不退回模拟签发。
- CSR create/get/delete、approval 子资源更新、指定 signer 的 approve；没有 CA 私钥、任意 signer、CSR status 写权限。
- 绑定资源的 get/create/delete 等必要操作，以及仅对配置角色的 `bind`。不给控制器直接绑定 cluster-admin，但如果允许它分发 cluster-admin，它仍是高权限代理。
- RBAC 本身不能按名称前缀或 label 限制 create；生产交付需配套准入约束限制控制器创建、变更、删除的绑定及 CSR，防止把“应用内校验”误当作集群侧强约束。
- 独立 opt-in overlay 管理控制器、RBAC、投射 token 与 API egress。现有 base 保持关闭；不把新增权限直接混入现网部署。
- 网络只放行需要的 apiserver 地址与端口；API Service DNAT 与实际 CNI 行为在集群验收，不开放所有 egress 代替验证。

依据：[RBAC bind 与提权边界](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/rbac/)。

## 阶段 3：下载 API、界面与验收

- `POST /api/v1/grants/{id}/kubeconfig`：现有会话认证、精确 Origin 校验、成员归属校验、限流与有界并发；管理员不能借此下载他人私钥。
- Web 在内存生成私钥并提交公共申请，有界等待控制器签发；超时或断开后标记 abandoned，不持久化私钥。重试生成新请求，原结果不得被另一个会话领取。
- 返回前重新验证会话、授权、证书与绑定执行状态。控制器不在线或状态过旧时失败关闭，不宣传下载可用。
- 授权表单提供明确的到期时间/长期有效选项，以及管理员可分配的凭据策略。成员只能查看既定期限并领取，不能自行切换为长期策略。
- 响应使用附件下载、`Cache-Control: no-store`，日志和审计不记录响应正文、私钥或完整 kubeconfig。审计区分申请、签发、准备交付、失败；HTTP 成功写出不等于证明用户已保存文件。
- 界面只增加下载按钮、凭据到期时间、实际权限状态与可操作的错误提示，沿用现有简洁样式及主题；授权到期和“回收中/失败”同时表达，不能把记录到期显示成已收权。
- 提供受管凭据记录：归属成员、授权、公开指纹、签发时间、实际到期时间、状态和审计；临近到期在平台提示换领。首版不依赖邮件等通知渠道。
- `/readyz` 仍表示 Web 基础就绪；签发能力另含 controller 心跳、目标配置和对账状态，不能仅设置静态 `kubeconfig_download=true`。

### 验收矩阵

| 场景 | 通过标准 |
| --- | --- |
| FreeIPA 登录 | 真实 admins 成员可管理；普通成员无管理员接口；账号关联稳定 |
| 正常授权 | 实际身份、角色与管理员分配一致，下载后无需插件即可 kubectl |
| 成员隔离 | 无法下载他人凭据；不能自选角色、主体、集群地址或签名用途 |
| 重复领取 | 新密钥、独立申请；同授权统一收权；数据库、日志、备份无私钥 |
| 有效期 | 普通策略最长 24 小时，运维策略最长 365 天；有限期授权再限制证书期限；不足 10 分钟明确拒绝 |
| 长期授权 | 不设到期仍可手动撤回；不因凭据刷新恢复已撤回权限；旧记录迁移不变成长期授权 |
| 策略隔离 | 成员不能通过修改下载请求或任务策略取得运维长证书；长策略不改变角色权限 |
| 撤回/到期 | 健康环境目标 30 秒内新业务 API 请求被拒绝；界面只在实测删除后显示已回收 |
| 无其他授权 | 检查独立主体及 `system:authenticated` 没有额外业务权限；发现旁路绑定先处理 |
| 长连接 | 分别记录 watch、exec、port-forward 在撤回后的行为，不承诺强制断开 |
| 失败与恢复 | API 不通、controller/Web 重启、并发撤回、重复执行都不会丢失回收意图或交付越权配置 |
| 旧备份恢复 | 控制器暂停并核对撤回记录后再启用，不自动复活历史授权 |
| 上线与回滚 | 本地、API 协议和隔离集群验证通过；备份后再交付 Argo，迁移回滚说明明确 |

30 秒是健康环境的验收目标，不是控制器或 apiserver 停机时的硬保证；硬的认证失效上限来自证书到期。凭据签发单元测试不能替代真实集群验收。

## 收权的明确边界

Kubernetes v1.35 不支持逐张客户端证书吊销。删除绑定撤回该授权提供的业务权限；证书仍可能通过认证并保有默认发现等公共权限，直到到期。已有流式连接不会因此获得强制断开保证。

2026-10-16 只读检查发现，当前集群的 `kubevirt.io:default` 和 `instancetype.kubevirt.io:view` 绑定给 `system:authenticated`，包含 KubeVirt 状态/版本与集群实例类型、偏好的读取权限。删除个人绑定不能回收这些公共权限。测试应明确区分它们和 KubeGrant 管理的业务权限；本次不修改既有共享绑定。

FreeIPA 禁用账号首先影响平台登录，已签发证书不自动询问 FreeIPA。账号停用联动回收需后续同步机制；本阶段要求离队或禁用时管理员显式撤回集群授权，不能把平台退出登录或禁用账号显示为已完成 Kubernetes 收权。运维证书最长 1 年，更不能依赖短期自然到期代替撤回。

长期凭据泄露时，撤回原授权并重新建立授权，使用新主体；只重新下载一份配置不会使旧私钥和证书失效。这里回收的是受管绑定提供的权限，不能吊销证书认证能力或保证断开已有连接。

`cluster-admin` 持有人能够创建其他授权或凭据，平台只能回收自己管理的绑定，不能保证收回管理员主动建立的旁路访问。上线前核实实际要沿用的角色，当前配置中的 `cluster-admin` 不能被当作所有成员的默认授权依据。

依据：[Kubernetes v1.35 认证机制](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/authentication/)。

## 发布顺序

1. 本地完成三个阶段与检查，保留关闭状态。
2. 隔离集群验证实际签名、角色绑定、到期与撤回；补齐真实 FreeIPA 登录验收。
3. 形成包含镜像、权限差异、数据库迁移、备份与回退步骤的可审阅发布变更，commit 前请用户确认。
4. 先限量测试账号与测试角色，再在现有 Argo/Harbor/openng 路径启用生产签发；保留原运维入口。
