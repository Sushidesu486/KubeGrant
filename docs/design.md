# KubeGrant 设计草案

状态：分阶段开发中。更新于 2026-10-16。

## 目标

构建基于 Kubernetes 的内部权限控制平台，对内分发受管理的个人 kubeconfig。管理员管理谁可以访问哪个集群、拥有哪些权限、授权何时结束，以及凭据签发和回收的实际结果。

当前背景是队内 kubeconfig 管理分发。首版身份来源、授权流程、技术栈与登录接入方式已确定；普通凭据最长 24 小时，固定运维成员采用长期授权与最长 1 年的个人证书，具体执行与验收见 [凭据签发开发计划](credential-plan.md)。

## 已确定的产品决策

- 首版由管理员直接为成员分配访问权限与有效期。
- 成员登录后查看自己的授权并领取对应的 kubeconfig。
- 首版由现有 FreeIPA 管理身份，作为过渡；KubeGrant 独立管理集群访问授权。
- GitLab 身份接入留待后续升级适配，首版不依赖 GitLab 登录或组同步。
- 首版沿用现有集群权限策略，先管理授权、领取与有效期；当前不需要“整集群只读”“指定 namespace 读写”“临时集群管理员”这三种预设档位。具体沿用哪些角色/身份绑定仍需在接入时核实，不据此推断所有成员都应具有管理员权限。
- 成员下载 kubeconfig 后直接使用 kubectl，不要求额外安装登录插件。
- 授权有效期与凭据有效期分别管理；管理员可为固定运维成员授予不设自动到期时间的长期授权，并显式分配 1 年证书策略。普通凭据保留 24 小时策略，长期策略不自动改变 Kubernetes 权限。
- 项目使用 Go 后端、React + TypeScript 前端。
- 前端使用简洁的工具界面，去掉宣传口号、装饰性英文标签、流程介绍和无必要的小字；只显示完成当前操作所需的信息。
- 支持浅色、深色和跟随系统三种主题选择，默认跟随系统，手动选择保存在本地浏览器。
- FreeIPA `admins` 组映射为 KubeGrant 平台管理员，与集群访问授权分别管理。
- 日常平台可部署在 k8s；保留独立的本地主机 SSH、BMC 和离线应急 kubeconfig，不将它们迁入平台。
- 创建 Git commit 前必须取得用户确认；当前搭建与验证不包含提交或推送授权。

已确定的术语见 [CONTEXT.md](../CONTEXT.md)。以下权限方案与凭据模型仍是草案。

## 建议的概念划分

以下是待讨论的模型，不代表已经确定的实现：

| 概念 | 含义 |
|---|---|
| 身份（Identity） | 授权所指向的成员身份；首版关联 FreeIPA 账号，稳定标识和后续迁移映射待设计 |
| 集群（Cluster） | 可以授予访问权限的目标 Kubernetes 集群 |
| 权限方案（AccessProfile，候选概念） | 管理员可分配的一组权限及适用范围；是否需要此概念待实际权限需求确认，不预设权限档位 |
| 授权（Grant） | 管理员授予某成员的集群访问许可，记录权限范围与有效期；权限方案如何表达待定 |
| 访问凭据（Credential） | 按授权所选策略签发的个人客户端证书与私钥；普通最长 24 小时，运维最长 365 天；每次领取生成新密钥，控制器与下载接口待接入 |
| kubeconfig | 提供给使用者的集群连接与认证配置 |

设计中分别描述授权和凭据的生命周期，明确“授权已撤回”到“实际请求被拒绝”的验收标准。

## 身份与授权的职责

FreeIPA 负责账号身份管理与身份核验；KubeGrant 记录成员的集群访问授权，不维护独立的成员密码。首版通过强制校验证书的 LDAPS，以登录用户自身凭据核验身份并读取本人资料。

平台登录身份与访问 Kubernetes 时使用的凭据分别设计。FreeIPA 核验平台登录，下一阶段通过 Kubernetes CSR 为个人签发客户端证书，两者分别管理生命周期。

为支持后续适配 GitLab，身份接入与授权管理应分别组织。建议授权关联平台内稳定的成员标识，外部身份作为映射；迁移时显式关联旧、新账号，避免仅按同名用户名自动合并。此处为设计建议，账号关联、停用与迁移验证流程仍待确定。

## 首版流程

1. 管理员登记目标集群与可分配的权限方案。
2. 为成员创建授权，指定范围与有效期。
3. 成员通过 FreeIPA 身份登录，查看自己的授权，领取 kubeconfig。
4. 使用领取的配置访问测试集群，验证允许与禁止的操作。
5. 授权到期或管理员撤回后，验证新登录、已有凭据和已有连接的行为，并保留操作记录。

管理员直接授权与成员登录领取已经确认；集群登记、权限方案、撤回操作及其生效语义仍需展开设计。

## 后续可拆分权限的候选清单

以下用于讨论扩展能力，不纳入首版已确认范围。可按资源类型、动作、作用范围组合权限，而不预设固定的用户等级。

| 能力 | 可对应的资源或子资源 | 说明 |
|---|---|---|
| 查看资源与事件 | pods、deployments、events 等 | get/list/watch，可限定 namespace 范围 |
| 查看容器日志 | pods/log | 与执行命令分别管理；日志可能含敏感信息 |
| 进入容器、传文件 | pods/exec；kubectl cp 通常依赖 exec | 可以在容器内执行命令 |
| 端口转发 | pods/portforward | 应用访问能力还取决于目标应用的认证 |
| 调整副本数 | deployments/scale、statefulsets/scale | 与修改整个工作负载分别管理 |
| 发布与删除工作负载 | deployments、statefulsets、jobs、pods 等 | 会影响运行代码、挂载及身份选择 |
| 管理配置与密钥 | configmaps、secrets | 普通配置与 Secret 内容访问分开 |
| 管理存储与入口 | persistentvolumeclaims、services、ingresses、httproutes 等 | 区分查看、变更、删除 |
| 维护节点 | nodes、pods/eviction 等 | 查看、不可调度标记、驱逐、标签/污点修改分别考虑 |
| 管理权限与集群扩展 | roles、rolebindings、clusterroles、clusterrolebindings、CRD、webhook 等 | 授权管理与业务部署分别表达 |
| 操作队内自研资源 | DevPod、MPI、Kueue 等实际资源 | “只能操作自己的实例”还需要身份归属设计 |

以上只是能力映射示例，不是完整的可部署 RBAC 清单；具体资源名称、动词与客户端所需附加读取权限需实际验证。依据：[Kubernetes v1.35 RBAC](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/rbac/)。

限制与设计注意：

- RBAC 权限累加，没有 deny 规则。若身份仍通过其他绑定获得 cluster-admin，增加窄权限角色不会降低实际权限。
- Secret 读取、容器执行、任意工作负载创建，以及 bind/escalate/impersonate 等能力可能形成提权路径，不能视为互相完全独立的安全隔离。[RBAC practices](https://v1-35.docs.kubernetes.io/docs/concepts/security/rbac-good-practices/)、[Authorization](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/authorization/)。
- “只允许重启，不允许改镜像”等字段级限制，不能只靠 Deployment patch 权限表达；需要额外约束。RBAC 也不提供按对象标签或创建者自动限定权限的通用机制。[RBAC](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/rbac/)。
- 沿用现有权限不等于共享同一份管理员 kubeconfig；建议后续凭据设计采用可归属到成员的独立身份，签发方式待定。

## 当前实现范围

已实现 Go HTTP 服务、FreeIPA LDAPS 身份接口、服务端会话、管理员创建/撤回授权、成员隔离查看、审计和 SQLite 持久化；前端提供对应界面。生产已配置 IPA CA 并部署身份与授权管理版本；真实账号的成员与管理员验收仍待完成，未接入的下载不开放。

当前已运行的 Grant 模型仍要求明确的结束时间，支持长期授权已经确定，将在后续模型和数据库迁移中接入；普通有限期授权默认上限仍为 30 天。默认会话 30 分钟。`ActiveAt` 是记录层的判断，不能替代 Kubernetes 侧的收权执行或凭据失效。凭据核心已支持 24 小时和 365 天策略，但尚未接通长期授权、签发控制器和下载 API，当前应用没有集群管理权限或 CA 私钥。

部署提供单实例 SQLite/RBD 的 k8s 模板和独立管理机 systemd 模板。备份和清空平台会话可从本地命令执行，不依赖平台登录。详见 [部署与应急运维](deployment.md)。

## 后续接入需要确定的问题

1. 现有权限接入：沿用哪些角色和绑定，如何为成员建立可追踪的独立访问身份？
2. 收权要求：是否必须即时生效，能否接受明确的最长失效延迟？
3. 部署范围：首版是否仅接入队内一个集群？
4. 接入长期授权与凭据策略的数据库迁移、管理员表单及证书到期换领提示。
5. FreeIPA 账号停用/组变更后的会话最长保留时限，以及未来迁移至 GitLab 的身份关联方式？
6. 按凭据签发计划接入 Kubernetes 侧的授权执行、回收与恢复对账，并验证实际生效延迟。

这些答案不阻塞当前身份与授权管理的联调，但应在替代现有 kubeconfig 发放与运维路径前确定。
